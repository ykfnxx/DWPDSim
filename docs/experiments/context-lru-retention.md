# context_lru：retention、淘汰粒度与容量实验

日期：2026-09-15。结果来自同一开发版本；实现、配置示例、sweep 和诊断脚本与本报告一同提交。原始 trace、Parquet、逐组统计和事件日志保存在忽略的 `build/` 下。

## 结论

- 在 slices 全天数据上，128 GiB、300s、beta=20 命中率损失0.2707个百分点，写入减少4.07%；诊断发现49.30%的 Drop 后仍有复用，同时28.84%的实际写入在窗口内未再访问。当前信号存在选择误差。
- unscaled 数据对该策略更有利：128 GiB、300s、beta=0 损失0.6978个百分点，写入减少30.91%。两份输入请求量和 context 分布不同，不能仅由文件名推断差异原因。
- 扩容至256 GiB并不保证开启retention后的命中率提升：容量影响淘汰时机，且固定alpha时候选预算随容量增大。未做机制消融，不能将变化单独归因于其中一项。
- 256 GiB、600s、beta=10：命中率94.4578%，写入减少20.89%，compute cost增加16.22%；600s、beta=20：94.6124%、13.89%、9.39%。需要按计算与写入的实际成本选择。

## 配置与指标口径

- 全部使用 `context_lru`、alpha=0.01、8 MiB/block、`infinite_storage`、关闭 storage hit 回填，每组冷启动并连续回放整个输入。128/256 GiB对应16,384/32,768 blocks。
- 除初始粒度消融外，固定当前段尾部淘汰上限64 blocks，动态粒度关闭；Dump与Drop均不向父段扩展。
- 有效retention = 基础retention + beta × 上次已完成请求的context增量。beta单位秒/block；增量为同session相邻请求长度差的非负部分，首次请求为0。
- 命中率是Memory+Storage连续前缀block命中率；第一处全局miss之后的后缀也统计为miss。compute cost = Σ(请求miss blocks × 请求context blocks)，单位block²，并非实测延迟。
- baseline关闭retention，相同容量与其他参数。Drop/淘汰 = 本组累计drop_blocks / evicted_blocks；同一block可重复计数。写入减少 = 1 − 本组写入 / baseline写入。所有写入量为逻辑block写入，不含MQSim物理写放大。
- finish不将剩余Memory强制刷写到Storage。各容量baseline写入量不同，写入减少按各自baseline计算。

## 复现

从仓库根目录执行：

```bash
uv sync --locked
uv run python benchmark/prepare_trace_jsonl.py \
  --source ../../traceGen/runs/daily-mixed-2m-unscaled/trace.jsonl \
  --output build/reproduce-unscaled
uv run python benchmark/context_adaptive_sweep.py \
  --dataset build/reproduce-unscaled/input.parquet \
  --output build/reproduce-unscaled/256g \
  --memory-blocks 32768 --alpha 0.01 --base-blocks 64 \
  --retentions-s 60,120,300,400,500,600 --betas 0,5,10,20 --jobs 6
```

128 GiB将memory-blocks改为16384；其他数据修改source。三阶段消融省略`--retentions-s`并传入`--retention-s 60 --betas 0,1,2,5 --gap-references-s 15,30,60,120,300 --max-blocks 1024`。

sweep输出逐组JSON、report.md、results.csv与provenance.json。诊断加`--diagnostics`，然后按README的Memory Drop诊断步骤选择job并运行`benchmark/memory_diagnosis.py`。逐事件日志可能较大；并发仅在独立模拟实例之间进行，计时不用于性能比较。
